## 1. 文档职责与执行原则

本文件把 PROJECT_SPEC 的 7 个 Phase 拆成 54 个 Unit，用于每次向 Codex 授权一段具体工作，同时学习其关键原理。它可以随实施调整，不重新定义产品范围、技术主线或阶段退出条件。

| 文档                              | 职责                        | 何时修改        |
| ------------------------------- | ------------------------- | ----------- |
| `AGENTS.md`                     | Coding Agent 的工作规则与验证要求   | 开发约定变化      |
| `docs/PROJECT_SPEC.md`          | 产品功能、架构、Phase、最终验收        | 产品或架构发生实质变化 |
| `docs/IMPLEMENTATION_PLAN.md`   | Phase → Unit、依赖、实施顺序与单元验收 | 拆分或实施顺序变化   |
| `docs/IMPLEMENTATION_STATUS.md` | 已实现内容、验证证据、限制和下一步         | 每次实施结束      |

PROJECT_SPEC 决定范围与阶段验收，AGENTS 决定开发行为；本计划不能覆盖二者。若发现冲突，先说明冲突和影响，不通过修改测试或降低验收来掩盖问题。

执行约定：

1. 默认每次授权一个 Unit。用户明确授权整个 Phase 时才推进该 Phase 的所有 Unit；不自动扩展到后续 Phase。
2. Unit 是一个可验证的工程增量。表中的依赖是进入条件，阶段内按编号顺序执行；即使两个 Unit 没有直接依赖，也不因此默认同时开发。
3. 只建立当前需要的模块、表和接口，不一次铺满未来目录。新增迁移保留已有数据，不重写已应用的迁移。
4. 每个 Unit 都完成实现、必要验证、状态记录和关键取舍解释。可以共用已有测试、fixture 与报告格式，避免每个 Unit 另起一套框架。
5. Mock 用于离线流程与策略验证；Live 用于真实模型、embedding、rerank 等能力验证。两者必须明确标记，缺少凭据时不能自动用 Mock 补成通过。
6. 知识、报告、事件、产物、Trace、评测结果的授权持续生效。不能为了先演示功能而把核心身份和权限拖到最后。
7. Phase 完成以 PROJECT_SPEC 第 20 节的退出条件为准。Unit 完成不自动意味着 Phase 已验收。
8. 一次 Unit 如果仍然过大，可以在其下面增加步骤或 `Unit N.M.a / N.M.b`，保留原编号和依赖；调整记录留在本文件，实际完成情况写 STATUS。

这里的 Unit 顺序是推荐实施路线，不是固定工期。无需把学习、实验或每个代码提交都拆成一个新 Unit。

## 3. Phase 1：工程底座与最小工作台

规格映射：F01、F04 的基础部分；PROJECT_SPEC 第 4、7、13–17、20 节。

阶段边界：完成真实后台执行与 UI，不实现 RAG、真实 Agent 调查、外部写入或沙箱。

### Unit 1.1 — 工程初始化与配置

- **依赖**：已确认的 AGENTS 与 PROJECT_SPEC。
- **学习重点**：`uv` 工程、Python 包安装、前后端开发进程与配置生命周期。
- **实现范围**：根目录 Python 3.12/uv 工程，安装 `backend/src/agenthub`；React/TypeScript/Vite/pnpm 工程；锁文件、Ruff/mypy、Pydantic Settings、`.env.example`、忽略规则、健康检查。依赖在实际安装时核对兼容并锁定，不照抄未经验证的版本。
- **验收**：后端包可导入，API 与前端可分别启动；前端 build 和基础静态检查通过；缺失必要配置有明确错误，凭据未写进仓库。
- **本次不做**：业务数据库、登录、任务、模型和未来目录占位。

### Unit 1.2 — 数据库、迁移与基础产物存储

- **依赖**：1.1。
- **学习重点**：AsyncSession 的请求/任务边界、事务、Alembic 与文件产物元数据。
- **实现范围**：Compose PostgreSQL/Redis，异步数据库基础设施；按当前功能逐步建表的迁移方式；开发文件卷版 ArtifactStore 与受限路径；基础错误结构和 `request_id`。文件字节与业务元数据分开，读取产物始终经受控服务。
- **验收**：新数据库能通过迁移建立结构，应用重启不清库；数据库会话按生命周期关闭；文件路径穿越被拒；健康检查能区分进程正常与依赖不可用。
- **本次不做**：Qdrant、完整对象存储部署或未来全量业务表。

### Unit 1.3 — Session 登录与安全请求

- **依赖**：1.2。
- **学习重点**：服务端 session、Cookie、密码 hash、CSRF 与开发同源代理。
- **实现范围**：users/sessions、Argon2id、登录/退出/当前身份 API；随机 token 的服务端 hash/TTL/撤销；Cookie 环境配置、修改请求的 CSRF/Origin 校验；Vite `/api` 同源代理与生产安全配置校验。
- **验收**：有效登录可读取身份，错误密码和撤销/过期 session 被拒；退出后旧 session 失效；非法 Origin/CSRF 修改请求被拒；生产配置不会静默使用不安全 Cookie 设置。
- **本次不做**：SSO/OIDC、自建身份管理平台。

### Unit 1.4 — 租户、项目、角色与资源授权

- **依赖**：1.3。
- **学习重点**：Principal、角色权限与资源范围的组合，服务端授权入口。
- **实现范围**：tenants/memberships/projects/resource_acl；Admin/Developer/Reviewer/Viewer；dev/test 幂等 seed 和两个模拟租户；项目列表与授权 service。身份、tenant、角色来自服务端，演示 Developer 与 Reviewer 分开。
- **验收**：两个租户和角色能登录；同名项目、伪造 tenant 字段、越权项目 ID 不扩大范围；重复 seed 不重复数据；非 dev/test 不能误启演示账户。
- **本次不做**：复杂组织树、生产默认密码或完整成员管理后台。

### Unit 1.5 — OrderLab 素材与初始评测格式

- **依赖**：1.4。
- **学习重点**：可复现故障、fixture provenance 与 Agent-visible/Grader-only 分离。
- **实现范围**：一个小型订单故障快照及最小公开复现测试；规范/OpenAPI/历史工单/JSONL 日志；fixture manifest、版本/hash、依赖与 `synthetic` 标记；最初约 3–5 个 case 的格式和受限公开输入。为后续 20 个审阅 case 保留统一格式。
- **验收**：通过受控测试证明最初故障确实存在；manifest 与素材匹配；公开输入不包含标准根因与隐藏断言；示例代码只作为素材，不被上传/入库过程执行。
- **本次不做**：20 个完整标注 case、全量评测平台或独立订单产品。

### Unit 1.6 — Run API、队列与持久状态

- **依赖**：1.4、1.5。
- **学习重点**：API 与 Worker 分离，任务状态机与请求幂等。
- **实现范围**：创建/列表/详情 run API；tenant/actor/operation 作用域的 Idempotency-Key 与请求 hash；Celery 只传 run ID；数据库 run 状态、持久事件和基础结构化日志；明确标识 MockModel 的短任务与真实后台结果。使用状态版本/原子转换防止重复消费同时推进同一基础任务。
- **验收**：创建请求不等待完整执行；同 key 同请求返回原 run、异请求返回冲突；页面关闭后 Worker 继续；失败有持久原因；跨租户访问被拒。
- **本次不做**：完整 outbox/租约恢复保证。将投递失败和长时间 queued 的限制记录下来，4.1–4.2 补齐，不能宣传为可靠恢复已完成。

### Unit 1.7 — 持久事件与基础 SSE

- **依赖**：1.6。
- **学习重点**：先持久化再推送、事件序号与浏览器连接生命周期。
- **实现范围**：run 内单调 seq 的事务分配与唯一约束；SSE/历史事件读取；状态和步骤事件；同源 Cookie 授权；断开清理与短事务数据库读取。保留最小 `after_seq` 补拉能力。
- **验收**：事件顺序可追溯，断开后后台任务继续；从已有 seq 能取得后续持久事件；跨租户事件读取被拒；SSE 等待不长期占用数据库 Session/事务。
- **本次不做**：完整保留期、通知丢失与撤权中途重连故障矩阵，4.7 完善。

### Unit 1.8 — OpenAPI 契约与最小工作台

- **依赖**：1.3–1.7。
- **学习重点**：OpenAPI 生成类型、TanStack Query 与 SSE 状态同步。
- **实现范围**：按实际 API 生成前端契约；登录/项目选择/任务创建/列表/详情；状态、步骤、结果、错误与 Mock 标签；项目切换清理缓存；最小导航和基本响应式。状态来自后端，不用定时器伪造进度。
- **验收**：浏览器完成登录→创建→查看后台结果；刷新后恢复已持久任务；前后端构建和相关权限/幂等检查通过；记录 Phase 1 验收与限制。
- **本次不做**：知识库、报告审批、Trace 实验页。

**Phase 1 Gate**：两个租户/角色登录，后台任务与真实后端 UI，run/event 隔离，请求幂等，后端检查与前端 build 均通过。演示结果明确属于 Mock，不证明真实 Agent 质量。

## 4. Phase 2：多源 RAG 与 Evidence Registry

规格映射：F02、F03；PROJECT_SPEC 第 8、12、18、20 节。

阶段边界：完成可独立调用的检索与证据服务。先衡量召回质量，再把检索放进 Agent；本阶段不实现自主调查和外部行动。

### Unit 2.1 — 来源入库、切分与证据合同

- **依赖**：Phase 1。
- **学习重点**：ingestion job、来源版本、chunk/parent、结构化位置与 evidence provenance。
- **实现范围**：sources/source_versions/index_jobs/chunks；上传与异步处理；Markdown/TXT、OpenAPI 本地受控引用、工单 JSON 解析；标题/endpoint/schema/字段切分；版本/hash/ACL/状态；固定 Evidence 与 location 联合 Schema，为所有检索实现共用。日志先保留结构化格式，不整批向量化。
- **验收**：格式/大小/编码/路径限制生效，恶意远程 `$ref` 不被请求；重复任务可防重或安全重试；chunk 可定位原文；失败原因与处理状态持久化。
- **本次不做**：PDF/OCR、模型语义检索、执行上传代码。

### Unit 2.2 — Dense 检索基线

- **依赖**：2.1。
- **学习重点**：embedding、向量空间、Qdrant collection、索引过滤与 Recall@k。
- **实现范围**：EmbeddingProvider、Qdrant 配置与批量索引；先实现 dense-only 查询；BGE-M3 本地或经验证的托管实现；模型/维度/index version；tenant/project/source/snapshot 过滤；最小检索接口和原文定位。MockEmbedding 使用独立索引空间。
- **验收**：标注的小批 query 能返回对应授权证据；错误维度/模型空间不混用；返回来源与位置；真实 embedding 的配置和实际结果留存，缺少条件则记 unverified。
- **本次不做**：稀疏融合、reranker 或宣称检索提升。

### Unit 2.3 — BGE-M3 学习型 Sparse 检索

- **依赖**：2.2。
- **学习重点**：学习型稀疏表示与 dense/BM25 的差异。
- **实现范围**：SparseProvider 合同与 BGE-M3 学习型 sparse 的真实输出适配；Qdrant 稀疏索引；sparse-only 策略；复用 Dense 的授权/版本过滤，单独记录表示版本。若 Dense 使用托管模型，不假定其同时提供 BGE sparse。
- **验收**：英文错误码、函数名、接口路径与中文描述样例都可独立评测；稀疏权重确实来自声明的实现；Dense 与 Sparse 结果可区分，不把 BM25 输出标为 BGE sparse。
- **本次不做**：RRF 或用不可用接口伪造稀疏能力。

### Unit 2.4 — BM25 与中文分词对照

- **依赖**：2.1、2.2。
- **学习重点**：BM25、分词、词法匹配与授权语料对统计量的影响。
- **实现范围**：小数据集 BM25 对照策略，采用 bm25s/经验证的中文分词方案；保留版本号、错误码、路径和符号；按授权语料分区建索引；固定语料版本，提供单独的 `bm25` 配置。
- **验收**：相同 query 和标注可运行 Dense/Sparse/BM25；同名资源跨租户不能召回；中文与精确符号的分词效果有可读样例；不把结果过滤当作唯一授权措施。
- **本次不做**：OpenSearch 部署或未经测量的生产规模承诺。

### Unit 2.5 — RRF 混合召回、去重与策略配置

- **依赖**：2.2–2.4。
- **学习重点**：rank fusion、各路 top-k、候选去重与分数解释。
- **实现范围**：主链路 Dense+BGE Sparse→RRF→去重；明确每个召回分支及过滤；BM25 作为独立对照，可提供命名清楚的 Dense+BM25 实验策略；记录候选排名、来源与融合方法；限制候选数量，不直接相加不可比的原始分数。
- **验收**：固定候选的融合次序可解释；重复 chunk 不反复占位；任一分支不会返回未授权/错误版本内容；同一检索服务能切换对照策略。
- **本次不做**：动态模型路由或默认宣称 Hybrid 更优。

### Unit 2.6 — Reranker 与 Parent 上下文扩展

- **依赖**：2.5。
- **学习重点**：cross-encoder 重排、召回与排序的不同职责、延迟与结果截断。
- **实现范围**：可替换 RerankProvider，验证 bge-reranker-v2-m3 或托管实现；对已授权候选重排；候选数量/长度/超时限制；parent/context 按需读取并重新鉴权；记录模型和参数版本，rerank 失败使用显式策略并标记降级。
- **验收**：同一候选集的排序前后可比较；真实 rerank 调用与耗时可追踪；parent 不引入未授权内容；失败不会静默把“未重排”包装成成功重排。
- **本次不做**：自动微调 reranker 或无限上下文扩展。

### Unit 2.7 — 代码、提交与结构化日志精确检索

- **依赖**：2.1、2.2。
- **学习重点**：代码/日志证据与文档语义检索的差异，固定快照与结构化时间线。
- **实现范围**：固定授权源码快照；受控 rg、符号/函数定位、必要 Tree-sitter 解析与 commit diff；日志按 service/request_id/时间/版本查询；参数化过滤、结果上限、路径与符号链接检查；统一返回代码行范围/日志事件位置的 Evidence。

## 6. Phase 4：可靠 Harness 与故障注入

规格映射：F08；PROJECT_SPEC 第 10、13–15、18、20 节。

阶段边界：在已有业务闭环上补齐任务调度、故障恢复与资源控制。复用 LangGraph 持久化机制，应用层实现业务一致性和策略。

### Unit 4.1 — Transactional Outbox 与投递恢复

- **依赖**：Phase 3。
- **学习重点**：数据库事务与消息投递的间隙，至少一次投递。
- **实现范围**：创建 run、补充输入、审批恢复在事务中写 outbox；dispatcher、重试/扫描、投递记录；Broker 中断后的恢复；迁移已有入队路径，保持 API 与业务状态合同。
- **验收**：业务提交后、发送队列前进程崩溃可恢复投递；重复 outbox 投递不重复逻辑动作；审批已提交但通知丢失不会永久卡住；数据库事务不依赖 Redis 原子提交。
- **本次不做**：自建通用消息中间件或承诺跨系统 exactly-once。

### Unit 4.2 — Lease、Heartbeat、Fencing 与 Run 恢复

- **依赖**：4.1。
- **学习重点**：Worker ownership、陈旧 Worker、checkpoint 与业务表独立一致性。
- **实现范围**：run_leases 原子领取、owner/过期/fencing token、心跳、恢复扫描；状态/事件/受控写入验证 ownership；等待状态释放 lease；列明各关键节点 checkpoint 与业务更新顺序、恢复规则和产物复用规则。
- **验收**：两个 Worker 竞争只有有效 owner 推进；旧 owner 不能覆盖新 owner 的状态或发起受控新动作；Worker 在取证/产物/审批关键点崩溃可恢复；checkpoint 前后故障有实际证据，不仅依赖框架说明。
- **本次不做**：认为本地 fencing 能撤回已发出的远程请求；在途副作用由 4.3 处理。

### Unit 4.3 — Unknown 动作对账与安全重试

- **依赖**：4.2、3.7。
- **学习重点**：请求/响应丢失、外部幂等与动作结果不确定性。
- **实现范围**：MockTicket 故障模式、外部稳定标记查询、reconcile API/恢复任务；核对目标和参数；找到已完成结果即保存 external_id；不能确认时保留 unknown 或转人工；明确何种证据允许再执行，禁止盲目重试写入。
- **验收**：远端已提交但响应丢失时对账找到唯一工单；明确未提交且有安全重试条件时才重试；结果无法判定不伪造 succeeded；权限/审批变化不会通过对账扩权；GitHub 适配器如缺少足够查询保障须写明限制。
- **本次不做**：把本地超时等同于外部失败，或靠重生成 action_id 绕过账本。

### Unit 4.4 — ContextManager 与大型产物引用

- **依赖**：4.2。
- **学习重点**：模型上下文与持久历史的区别，摘要必须保留的约束。
- **实现范围**：大型日志/工具输出保存 ArtifactStore；state/prompt 使用引用与有限摘要；压缩保留目标、资源范围、关键事实、evidence_id、未决事项、审批状态和预算；按需授权加载原文；摘要版本与来源追踪。
- **验收**：构造长调查仍能追溯原文；摘要不丢批准要求与权限；撤权后引用无法重新读取；重试/恢复不丢关键未完成项；比较压缩前后长度与一次代表任务行为。
- **本次不做**：把模型猜测自动写成长期事实，或建立独立长期记忆产品。

### Unit 4.5 — 完整预算、分类重试与第二供应商

- **依赖**：4.4、3.1。
- **学习重点**：费用/时间/步数/工具次数、重试成本与供应商能力差异。
- **实现范围**：BudgetManager 完整限制和持久 usage；调用前检查/预留，调用后结算；运行时间与人工等待区分；临时错误有限退避、权限/参数错误不重试；第二供应商能力验证与显式切换/受控降级；估算 usage 与价格版本；硬超时/在途调用的预算剩余风险说明。
- **验收**：各类限额到达后保存部分结果并停止新增调用；重试成本计入；第二供应商 Tool Calling/结构化输出/usage/错误有实测或明确未验证；降级不扩大权限、不切 Mock；未知 usage 不按零处理。
- **本次不做**：复杂动态选模、模型训练或“预算绝不超出”的无条件承诺。

### Unit 4.6 — 取消、超时与资源清理

- **依赖**：4.2、4.3、4.5。
- **学习重点**：cooperative cancellation、在途请求和已产生外部效果。
- **实现范围**：cancel API 的权限/状态版本、Worker 轮询与节点边界检查；模型/工具超时；临时资源清理；waiting_input/approval 可取消；取消后 unknown 仍允许只读安全对账，记录已完成的外部效果。
- **验收**：取证、模型调用、审批等待、行动在途各阶段取消都有明确结果；取消后无新写动作；已创建工单不被假装撤销；unknown 不被丢弃；不占用永久 lease。
- **本次不做**：依赖 Celery 强杀作为唯一取消方案或自动删除外部工单。

### Unit 4.7 — SSE 重连、权限变化与保留期恢复

- **依赖**：4.1、4.2、1.7、1.8。
- **学习重点**：持久事件作为恢复来源，客户端去重与 snapshot 重建。
- **实现范围**：Last-Event-ID/after_seq、run_id+seq 去重；Redis 通知丢失时数据库补拉；事件保留期与明确恢复响应；前端拉取当前 snapshot 后继续；SSE 长连接期间权限变化检查与资源清理。
- **验收**：网络断开/浏览器刷新/通知丢失不丢状态；事件不重复展示；过旧 seq 有清楚恢复路径；撤权后停止返回事件与受保护状态；任务执行不依赖浏览器连接。
- **本次不做**：把 UI SSE 当作 MCP 传输或把长期 token 放 URL。

### Unit 4.8 — 故障注入矩阵与 Harness 验收

- **依赖**：4.1–4.7。
- **学习重点**：从中断点检查恢复状态、账本和外部环境，成功不是单看 completed。
- **实现范围**：模型限流/工具超时、Worker 崩溃、队列投递丢失、checkpoint/业务更新间隙、陈旧 owner、响应丢失、取消/预算故障矩阵；可重复脚本与 grader；每次重置到相同初始环境，记录 run/action/外部对象与失败分类。
- **验收**：覆盖的崩溃点可恢复；已确认动作不重复，unknown 可审查；等待不持持续 lease；输出真实故障报告、剩余风险与演示步骤；第二供应商能力状态列明。
- **本次不做**：以 Mock 故障恢复收益表述为真实模型推理提升。

**Phase 4 Gate**：outbox、ownership、checkpoint 一致性、未知写入、取消和预算都有实际验证；已确认动作无重复，无法判定的动作不盲重试；SSE 可恢复；两供应商能力验证或明确限制；阶段未验证项不能隐藏。

## 7. Phase 5：受限 Multi-Agent 与 Skill Registry

### Unit 5.1 — 子任务合同与 Coordinator 路由

- **依赖**：Phase 4。
- **学习重点**：任务拆解、能力委派与简单/复杂任务判断。

### Unit 5.2 — Evidence/Log/Code 子图的串行分工

- **依赖**：5.1。
- **学习重点**：职责边界、专用工具集合与结构化返回。
- **实现范围**：Evidence/Log/Code 调查子图，先串行运行；各自 scope/tools/prompt；返回 facts/hypotheses/evidence/conflicts/missing/next_steps；共享 Evidence Registry，以引用传递，避免复制完整对话；Code 仍只读。
- **验收**：同一事件得到三类可定位证据；Log 无法使用 Code 工具扩大范围；子图不能直接创建工单；单 Agent 与串行分工均可运行，形成后续并行对照。
- **本次不做**：同时修改源码或每个角色再建一套服务。

### Unit 5.3 — 受限并行、命名空间与预算预留

- **依赖**：5.2、4.5。
- **学习重点**：并行共享预算、状态合并与父子运行一致性。
- **实现范围**：最多三个并行调查；独立输出槽位/命名空间；每个子 Agent 的工具/资源白名单与 deadline；父预算原子预留/结算；所有输出写入受父 ownership 约束；检查取消与恢复路径，避免多子图竞争覆盖状态。
- **验收**：并行预算不能各自使用整份父预算；结果合并不丢字段；子 Agent 无法扩权；父取消后停止新增调用；恢复不重复已完成的调查结果或引入外部新副作用。
- **本次不做**：无限并发、独立子 Agent 绕过 Harness 或自动扩容集群。

### Unit 5.4 — 冲突汇总、Verifier 与部分结果

- **依赖**：5.3、3.4。
- **学习重点**：证据冲突、验证与投票的区别，超时后的合格交付。
- **实现范围**：显式 evidence merge/冲突检查；Verifier 检查来源、版本、支持性与缺失；有限补查；失败/超时子任务返回部分结果；超过预算后给出未知或请求输入；沿用报告/行动状态机。
- **验收**：相互矛盾结果不会多数票决定根因；旧规范能被识别；一个子图超时不无限阻塞父任务；Verifier 无批准权限；不充分结果不会被包装为已确认事实。

### Unit 5.5 — 项目内 Skill Registry 与版本治理

### Unit 5.6 — 单 Agent、串行与并行的真实对照

- **依赖**：5.1–5.5、2.9、3.8。
- **学习重点**：公平实验、总预算、延迟与每成功任务成本。
- **实现范围**：同一组任务/快照/检索策略/模型与总预算；对照单 Agent、串行分工、并行调查；记录策略版本、工具/模型重试、输入输出、每次初始环境和重复次数；工作台显示实际路径、子步骤与结果；失败 case 归档。
- **验收**：真实 Live 实验可复现，报告成功/成本/延迟和不确定性；简单任务无收益保留单 Agent；没有 Live 条件只验协作工程，不宣称质量收益；保留不同路径的失败证据。

**Phase 5 Gate**：委派不扩权，预算/并行有界，冲突/超时/部分结果可处理；有相同总预算下的真实对照；无收益任务保留单 Agent，Skill 版本可追踪。

## 9. Phase 7：ReleasePilot 扩展

规格映射：F12；PROJECT_SPEC 第 11–12、19–20 节。

阶段边界：固定受控 FastAPI fixture，先做可验证修复，再做草稿 PR。仅执行允许源码与配方，不自动合并、生产发布或声称支持任意代码。

### Unit 7.1 — 独立 Sandbox Runner 与隔离合同

- **依赖**：Phase 6。
- **学习重点**：受控执行环境、凭据与执行面的分离、容器隔离的实际边界。
- **实现范围**：独立 Runner 与 create_sandbox/run_test/apply_patch 合同；预构建/锁定依赖；非 root、CPU/内存/进程/磁盘/时间限制、工作目录/网络策略；只挂授权快照和产物目录；不挂平台工程、grader、数据库卷、密钥或宿主 Docker socket；Repo/Sandbox MCP 扩展沿用 Gateway 策略。
- **验收**：资源/时间/路径/出站限制可验证；沙箱读不到平台凭据/隐藏评分材料；生命周期和取消清理可测；明确普通 Docker 演示不构成强恶意代码隔离承诺。
- **本次不做**：不可信公网仓库接入、自由 shell 产品接口或 K8s 强隔离集群。

### Unit 7.2 — 固定快照与故障复现

- **依赖**：7.1、OrderLab manifests。
- **学习重点**：环境一致性、复现 recipe 与原始失败证据。
- **实现范围**：snapshot/hash/base commit 校验；已批准运行配方和模板参数；公开最小复现；stdout/stderr/exit code/耗时/环境版本归档；故障版本与正常版本验证；无法复现时返回限制或更多信息需求。
- **验收**：原始故障快照确实失败，正常快照通过对应条件；重复运行可复现；缺失依赖与无故障结果不被描述为已确认代码问题。
- **本次不做**：在复现前盲目生成补丁或提供隐藏测试。

### Unit 7.3 — Code Agent 单写入者与 Patch 产物

- **依赖**：7.2、5.2。
- **学习重点**：基于固定基线修改、patch provenance 与改动范围。
- **实现范围**：Code Agent 在独立工作目录执行受限补丁；唯一写入者；path/符号链接/文件类型/大小/依赖变更策略；保存 base commit、patch hash、修改清单和 diff；Verifier 读取固定 patch 快照；加入项目内 verified_patch skill 的初始版本。
- **验收**：diff 可在相同基线上干净应用；多 Agent 不竞争写入；不能修改评分器/隐藏文件/平台策略；删除测试、屏蔽错误、扩大权限等投机补丁不能当作有效修复。
- **本次不做**：自动提交仓库或让不同 Agent 各自修改后随意合并。

### Unit 7.4 — 公开测试、回归与有界修复迭代

- **依赖**：7.3。
- **学习重点**：复现测试与回归测试，失败驱动的有限迭代。
- **实现范围**：公开测试和回归配方；针对幂等任务覆盖同键同参/异参、并发、超时重试；保存命令模板/输出/退出码/版本；测试失败反馈给 Code Agent 的次数与预算限制；Runner 超时/失败清理。
- **验收**：原失败转为通过，关键回归真实运行；达到迭代上限保存失败和未解决项；测试超时不能计通过；保留原始测试与补丁后结果，可重复比较。
- **本次不做**：用 Agent “全部通过”文本替代测试结果或接入隐藏答案。

### Unit 7.5 — 独立隐藏 Grader 与错误补丁验证

- **依赖**：7.4、6.4。
- **学习重点**：独立验证环境、评测泄漏与评分器有效性。
- **实现范围**：独立 grader 身份/进程/挂载/环境，只接收固定基线与 patch；全新环境运行隐藏测试和关键回归；Agent 仅收到受控 verdict/必要失败分类，不收到答案或隐藏源码；正确/错误补丁或 mutation 检查，版本化 grader 结果。
- **验收**：故障基线失败、正确补丁通过、代表错误补丁被识别；Agent 无法经代码/知识/工具/沙箱读取 grader；仅另建一个目录不视为隔离；结果不能被补丁篡改。
- **本次不做**：在 Agent 沙箱挂载隐藏测试或把整个 grader manifest 放入工具输出。

### Unit 7.6 — Patch/Test 审阅与固定批准

- **依赖**：7.5、3.6。
- **学习重点**：代码产物批准与工单参数批准的共同机制及差异。
- **实现范围**：diff、复现/公开测试/隐藏 verdict、风险/未解决项/回滚建议 UI；Repository/目标分支/base commit/patch hash 的动作草稿与审批；Reviewer 固定批准；patch 或目标/base 变化后批准失效；前端显示验证来源与范围。
- **验收**：改动后的 patch 无法用旧批准执行；自审/过期/撤权被拒；审阅时可追溯真实测试产物；失败/证据不足可结束而不创建 PR。
- **本次不做**：批准者修改一句文字就默认批准所有未来补丁，或自动合并。

### Unit 7.7 — RepositoryConnector 与草稿 PR

- **依赖**：7.6、4.3。
- **学习重点**：分支/commit/push/PR 多步外部效果，动作账本与对账。
- **实现范围**：先提供独立可持久 Mock 仓库适配，再实现明确授权 GitHub 目标；执行器检查权限/批准/base/hash/ownership；稳定分支与 commit/PR 标记，记录各步骤 external refs；创建 draft PR；凭据只在受控 Connector；branch push 与 PR 响应丢失均有对账，未知时停止新增写入。
- **验收**：批准后目标存在对应 patch 的草稿 PR；拒绝/篡改/base 改变无发布；重复恢复不再创建同一逻辑 PR；途中 push 成功但 PR 未确认可审查恢复；真实授权仓库验证与 Mock 结果分开。
- **本次不做**：自动合并、生产发布、盲删远程分支或把 Git token 交给 Code Agent。

### Unit 7.8 — 修复评测、故障恢复与 V3 交付

- **依赖**：7.1–7.7。
- **学习重点**：修复成功、回归保持与执行可靠性分层报告。
- **实现范围**：Runner 崩溃/超时、取消/预算、patch 恢复、PR/push 响应丢失、安全边界故障集；修复任务独立 grader 与成本报告；Runbook、架构/接口/支持环境更新、演示材料；核对 V1/V2 回归。
- **验收**：至少主故障类有原失败、有效补丁、独立隐藏验证和 PR 审阅/执行证据；错误补丁/越界/未批准写入被识别；Runner 清理可验证；报告真实支持 Python/FastAPI 受控 fixture 的范围。无 macOS 时不声称已完成 iOS 构建验证。
- **本次不做**：为了扩大简历范围宣称通用自治修复；真实 PR 未验证时明确 pending。

**Phase 7 Gate**：隔离 Runner、复现、受限 patch、公开/独立隐藏测试、固定批准、草稿 PR 和故障恢复均有证据；原始故障失败、正确补丁通过、错误补丁被识别；真实支持范围和未验证集成写清楚。

1. AGENTS/PROJECT_SPEC/本计划/STATUS 的当前版本与仓库现状。
2. 依赖 Unit 的代码和验证证据是否存在；不能只看 STATUS 的“完成”文字。
3. 当前 Unit 的验收需要哪些服务、硬件、模型配置与授权目标。
4. 现有工作是否有未提交修改，确保本次实现不会覆盖。

退出 Unit 时提交：

- 可运行实现及相关契约、迁移、配置说明。
- 适合本次变化的验证证据：关键合同/策略/并发/恢复测试或真实集成结果；文案/布局微调不额外制造镜像实现的测试。
- `IMPLEMENTATION_STATUS.md` 的事实记录，包括命令/环境/结果/模式/未验证项。
- 1–3 个关键设计取舍解释，连接到当前实现。
- 下一步 Unit 及其进入条件。

验证范围按变化选择，不默认每个 Unit 重跑所有昂贵 Live 评测；相关检查通过后，只有新变化、失败或未解决风险才扩大验证。

### 10.2 状态定义

| Unit 状态     | 含义                     |
| ----------- | ---------------------- |
| planned     | 尚未开始                   |
| in_progress | 正在实施                   |
| implemented | 工程已实现，但必要验证仍有未完成项      |
| verified    | 当前 Unit 的必要验收全部有实际通过证据 |
| blocked     | 有明确障碍，无法完成当前必要工作       |

具体验收项分别使用 `verified / unverified / blocked`。例如“Mock 工单闭环 verified、Live 模型 smoke unverified”时，Unit 不能标成全部 verified。能继续完成的工程工作继续，不因一项凭据缺失停止整个项目；后续依赖真实质量验收的阶段保持待验收。

## 11. 学习与 Codex 的实际使用

学习围绕当前 Unit 的实现展开。每次优先掌握一个主问题，例如“为什么 SSE 不能决定任务生命周期”“为什么 checkpoint 不能证明外部写入没发生”“RRF 为什么不用原始分数相加”。无需在开始前学完所有框架。

推荐流程：

1. 阅读当前 Unit，确认输入、产物与验收；在学习对话里解释其原理和取舍。
2. 交给 Codex 实现当前 Unit；实现过程中把不理解的具体代码/状态/失败拿回学习对话讨论。
3. 检查演示与验证证据，要求解释关键路径；更新 STATUS 后进入下一 Unit。
